# WinniePro Remodeling Portfolio

This change builds the full portfolio website on top of the Next.js template. The Amplify Gen2 backend is extended with `Project` and `Photo` models and an S3 bucket, all authorization is split between authenticated (write) and guest (read) rules. Four pages are delivered: homepage with hero + category filter, `/projects/[id]` with photo grid and lightbox, `/upload` for mobile-first multi-photo ingestion, and `/admin` for project management with delete. CSS Modules are used exclusively; the three brand colors are defined as CSS variables and applied consistently.

**Watch for:** `CategoryBadge` has a confirmed bug where `LIVING_ROOM` only strips the first underscore — all current categories happen to work, but the fix is one character. The lightbox opens with focus on the close button but has no focus trap — tab key exits the modal into background content. S3 objects are intentionally not deleted when a project is removed (acknowledged in a code comment), but the UX implication is undocumented orphan storage. The `AmplifyProvider` loads config with a `fetch` at runtime, which means there is a window where the Amplify client is unconfigured and any data call on first render may silently fail.

**Verdict**: NEEDS_CHANGES

---

## High-level view

The four required pages exist and meet the feature spec. Auth gating is correct: `/upload` and `/admin` wrap in `<Authenticator>`; homepage and project detail have no auth import. The Amplify data layer uses `Schema["Project"]["type"]` and `Schema["Photo"]["type"]` throughout — no `any` types.

The upload form uses `font-size: 16px` on inputs to suppress iOS auto-zoom. The sticky upload button and single-column layout are correct mobile-first choices.

ProjectCard issues one `Photo.list` per card to find the cover image — an N+1 pattern that degrades as the project grid grows.

On delete, Photo DynamoDB records are removed but S3 objects are not. Explicitly commented as v1 behaviour, but no S3 lifecycle rule exists yet to reclaim orphan storage.

`AmplifyProvider` defers `Amplify.configure` to a `fetch` inside `useEffect`. Pages call `generateClient` at module scope, before the config arrives. On a slow load the first data call may fire against an unconfigured client and silently return nothing.

<details>
<summary>Issues (4)</summary>

1. **CategoryBadge underscore bug** — `replace("_", "")` replaces only the first underscore. `LIVING_ROOM` produces `livingroom` correctly by coincidence (one underscore), but any future two-underscore category will break. Change `replace("_", "")` to `replace(/_/g, "")` for safety and correctness.

2. **Lightbox focus trap missing** — The lightbox focuses the close button on open but does not confine tab navigation. Tab out of the close/prev/next buttons cycles into background page content behind the modal. Add `inert` on the background or a manual focus-trap loop between the three interactive elements.

3. **AmplifyProvider config race** — `Amplify.configure` is called inside `useEffect` after a `fetch`. Any `generateClient` call that fires during the first render (including `observeQuery` in `page.tsx`) runs against an unconfigured client. Consider loading `amplify_outputs.json` in the server layout and passing it as a prop, or block rendering until config resolves.

4. **Admin photo count N+1 on load** — `AdminDashboard` fetches photo count per project with a `Photo.list` for each row in parallel. With many projects this fires O(n) DynamoDB queries simultaneously. Consider storing a `photoCount` field on `Project` and incrementing it on upload, or batching the count queries.

</details>

<details>
<summary>Details</summary>

### CategoryBadge underscore strip

`CategoryBadge` generates a CSS module class name with:

```ts
category.toLowerCase().replace("_", "")
```

`String.prototype.replace` with a string literal replaces only the first match. `LIVING_ROOM` → `livingroom` works because there is a single underscore. All six current categories survive, but this is fragile. The correct form is `replace(/_/g, "")`. **Confirmed** — category values are defined in `amplify/data/resource.ts` and the replace call is in `CategoryBadge.tsx:30`.

### Lightbox focus trap

`role="dialog"` and `aria-modal="true"` are present, but without a focus trap or `inert` on the background, the browser's default tab order moves focus out of the overlay. Screen readers and keyboard users can reach background content while the modal is open. **Confirmed** — `Lightbox.tsx` has no `inert`, tab-cycle handler, or equivalent guard beyond the initial `closeRef.current?.focus()`.

### AmplifyProvider config race

`generateClient<Schema>()` is called at module scope in all four page files — before any component mounts. `Amplify.configure` runs inside `useEffect` after a `fetch` in `AmplifyProvider`. The `observeQuery` subscription in `page.tsx` also fires in a `useEffect`, so it runs after one event-loop tick past mount, which is usually enough time for a local `fetch("/amplify_outputs.json")` to complete — but not guaranteed on a slow connection. A failed-open client silently returns empty results with no error banner. **Likely** — race window confirmed by reading the module-scope `generateClient` calls and the async config path.

### S3 orphan objects on project delete

`AdminDashboard.handleDelete` removes DynamoDB `Photo` records but skips S3 objects. The comment at `admin/page.tsx:78` acknowledges this. Without an S3 lifecycle rule or a Lambda trigger on `Photo` delete, orphan objects accumulate with no recovery path. **Confirmed.**

### N+1 photo count in admin load

`AdminDashboard` loads the project list then, for each project, issues a separate `Photo.list` with a `projectId` filter. With 20 projects this fires 20 parallel DynamoDB queries. AppSync has per-connection concurrency limits and each query has latency overhead, so this pattern will produce visible load delays as the project count grows. **Confirmed** — `admin/page.tsx:40-47` shows the `Promise.all` over per-project photo list calls.

</details>
